# Features

Reference description of the traffic features used in *Energy-Aware Assessment and Energy
Modeling for Encrypted Video KQI Prediction at the Edge*. Section III-A of
the paper compresses the whole feature design into one paragraph; this document states, for
every stage, which quantity is computed from which field, so that the features can be
re-implemented exactly.

Everything below is traced to a file. Where a quantity could not be determined from the
released code and data, the document says so instead of guessing.

## 1. Naming

### 1.1 Traffic views

Four traffic views are compared. The paper names and the code names differ; the code name is
what appears in the Optuna study names, in the file names under `importances/`, and in the
`--scenario` / `filter` arguments of the capture scripts.

| Paper name | Code name | Keeps | Optuna study name | `capturing.py` scenario |
|---|---|---|---|---|
| ALL | `all_packets` / `all` | all packets of the video flows | `<family>_all_packets` | `header_only` |
| ALL>100B | `gt_100` | only packets above the 100 B threshold | `<family>_gt_100_packets` | `header_only_gt_100` |
| UL | `uplink_only` | only uplink packets | `<family>_uplink_only_packets` | `header_only_uplink_only` |
| UL>100B | `uplink_only_gt_100` | only uplink packets above the threshold | `<family>_uplink_only_gt_100_packets` | `header_only_uplink_only_gt_100` |

In the code the view is a pair of booleans, `uplink_only` and `gt_100`
(`preprocessing.py:86-95`). In the Optuna databases the view is not a hyperparameter: each of
the 12 databases holds four studies, one per view, with `study_id` 1 = `all`,
2 = `uplink_only`, 3 = `gt_100`, 4 = `uplink_only_gt_100`
(`config_controller.py:495`; the same order is assumed by `reconstruct_configurations.py`).

Note the direction of the `gt_100` flag inside the name generator: `gt_100 = True` keeps only
the `_gt_100` half of the feature block, and `gt_100 = False` keeps both the `_gt_100` and the
unsuffixed half (`preprocessing.py:52-53`). The ALL view therefore contains both size classes;
ALL>100B contains only the large-packet class.

### 1.2 Feature names

The canonical name of a feature is

```
{window}s_{dir}_{agg}_{iat|size}[_gt_100]        statistics
{window}s_{dir}_{packet_count|total_bytes}[_gt_100]   counts
```

with `window` ∈ {1, 3, 5, 10, 20, 30}, `dir` ∈ {`ul`, `dl`}, `agg` ∈ {`mean`, `median`,
`min`, `max`, `std`}. Examples: `1s_ul_mean_iat_gt_100`, `30s_dl_total_bytes`.

The generator is `feature_names_from_config` (`preprocessing.py:46-64`). A character-identical
copy exists in `feature_selection.py:37-55`. `code/features/make_feature_names.py` is a
verbatim port of both, copied rather than imported because `preprocessing.py` imports
`paths.py`, which hard-codes absolute paths of the machine the thesis was run on.

### 1.3 Dataset variants

The search treats the feature set as a hyperparameter. The `dataset` categorical of each
Optuna study takes these values (decoded from `trial_params.distribution_json` in `model_hpo/`):

| Variant | Available to | Meaning | Stored matrix |
|---|---|---|---|
| `multiple_windows` | all six families | all features of the view, for the selected window set | `dataset_n288_i1.0_w1-3-5-10-20-30_ffill[_scaled].npy` |
| `multiple_windows_fs` | all six families | the surviving feature set after selection, for the selected window set | same matrix, column subset |
| `dl_1s` | CNN, LSTM, TF only | a single 1 s window (48 / 24 / 24 / 12 features) | same matrix, the `1s_*` columns |
| `dl_0.5s` | CNN, LSTM, TF only | a single 0.5 s window, updated every 0.5 s | `dataset_n48_i0.5_w0.5_ffill_scaled.npy` |

Sources: the `dataset` distribution in all 12 databases (RF, LGBM and FFNN studies offer only
`multiple_windows` and `multiple_windows_fs`; CNN, LSTM and TF studies offer all four), and
the dispatch in `model_training.py:108-119` and `run_models.py:26-36`.

`dl_0.5s` maps to the dataset directory `n48_i0.5_w0.5`, built by
`build_features_from_config` (`preprocessing.py:303-330`) with `execution_interval = 10**9/2`
and `windows = [0.5]`. **No selected configuration uses `dl_0.5s`** (see §4);
`run_models.py:26-36`, which produced the full-test predictions, does not even implement that
case.

The role names also differ between paper and code: the paper's *performance-first* is
`performance` in every file name, and *energy-aware* is `efficiency`
(`config_controller.py:511`).

## 2. The base feature set

### 2.1 What is computed

For each (direction, size class) pair the pipeline computes twelve base features
(`feature_extraction_offline.py:6-27`, called from `preprocessing.py:290`):

| # | Feature | Metric key | Computed from |
|---|---|---|---|
| 1-5 | mean, median, min, max, SD of the inter-arrival time | `iat` | `window["timestamp"].diff().agg([...])` |
| 6-10 | mean, median, min, max, SD of the payload size | `packet_size` | `window["size"].agg([...])` |
| 11 | packet count | `packet_count` | `len(window)` |
| 12 | byte count | `total_bytes` | `window["size"].sum()` |

Timestamps are nanosecond integers (`preprocessing.py:116`), so the inter-arrival-time
features are in nanoseconds. `size` is the transport payload length — see §6, this is the
single most important detail of the whole feature design.

The aggregation order inside the stored matrix is `["mean", "median", "min", "max", "std"]`
and the metric order is `["iat", "packet_size", "packet_count", "total_bytes"]`
(`preprocessing.py:71-83`). The paper lists the statistics as "mean, median, standard
deviation, minimum, and maximum"; that is the same set in a different order. The CSV files in
`data/features/` give the order that the matrix columns actually follow.

If a window holds exactly one packet, the five inter-arrival-time features are set to NaN
rather than to 0 (`feature_extraction_offline.py:17-18`). If a window holds no packet at all,
the whole 48-value block for that window is set to `pd.NA` (`preprocessing.py:291`).

### 2.2 The counts

Per window: 12 base features × (1 or 2 directions) × (1 or 2 size classes). In total: × 6
windows.

| View | Directions | Size classes | Per window | Total (6 windows) |
|---|---|---|---|---|
| ALL | ul, dl | >100 B and all | 12 × 2 × 2 = **48** | **288** |
| ALL>100B | ul, dl | >100 B only | 12 × 2 × 1 = **24** | **144** |
| UL | ul | >100 B and all | 12 × 1 × 2 = **24** | **144** |
| UL>100B | ul | >100 B only | 12 × 1 × 1 = **12** | **72** |

**Verified against the generator, not against the paper's paragraph.** Running
`code/features/make_feature_names.py` executes the ported `feature_names_from_config` and
asserts that the ALL list has 288 distinct entries; it prints 48/24/24/12 per window and
288/144/144/72 in total, matching the table above and the paper. The script also asserts that
the generator's output order equals the order obtained by sorting the view's features by their
index in the 288-element ALL list, which is the order `feature_indices_per_scenario`
(`preprocessing.py:97`) actually feeds to the models. The two orders agree for all four views,
so the published CSVs are both the matrix-column order and the model-input order.

The `index` column of the CSVs is the column index into
`dataset_n288_i1.0_w1-3-5-10-20-30_ffill.npy`. Column 288 of that matrix is the sample id,
which `get_dataset` overwrites with the target (`machine_learning_helpers.py:20-40`); it is
appended to every index list by `feature_indices_per_scenario` and is not a feature.

## 3. Windows

### 3.1 The stored window set

Features are computed over sliding windows of **1, 3, 5, 10, 20 and 30 s**, all ending at the
same instant, and the whole 288-value vector is emitted **once per second**
(`preprocessing.py:279-300`, with `execution_interval = 10**9` and
`windows = [1, 3, 5, 10, 20, 30]`; the dataset directory name `n288_i1.0_w1-3-5-10-20-30`
encodes exactly this).

A window is a half-open-looking but in fact closed interval:
`df_traffic["timestamp"].between(next_execution_time - window_length, next_execution_time)`
(`preprocessing.py:289`), i.e. both endpoints are included.

There is a second, unused window-set generator in the same file,
`build_scenario_features` (`preprocessing.py:26-43`), which lists windows
`(1, 2, 3, 5, 10, 20)`. It is dead code: no 2 s window exists in any stored dataset, and no
Optuna study references it.

### 3.2 Which maximum window a search could select

The window set is a hyperparameter, `feature_window_size`, with four values. Its expansion is
`window_lengths` in `model_training.py:18-23`, `run_models.py:13-18` and
`feature_selection.py:91-96` (the three copies agree):

| `feature_window_size` | Windows used | ALL | ALL>100B | UL | UL>100B |
|---|---|---|---|---|---|
| `up_to_5s` | 1, 3, 5 | 144 | 72 | 72 | 36 |
| `up_to_10s` | 1, 3, 5, 10 | 192 | 96 | 96 | 48 |
| `up_to_20s` | 1, 3, 5, 10, 20 | 240 | 120 | 120 | 60 |
| `up_to_30s` | 1, 3, 5, 10, 20, 30 | 288 | 144 | 144 | 72 |

These counts are printed by `code/features/make_feature_names.py`. The paper's phrase
"longest window 5-30 s" in the (commented-out) search-space table of `methodology.tex:34`
refers to these four choices.

### 3.3 The single-window variants for sequence models

The CNN, LSTM and transformer studies may instead select one single window:

* `dl_1s` — the 1 s window only, taken as a column subset of the same 288-feature matrix
  (`feature_indices_per_scenario(scenario=view, windows=[1])`, `run_models.py:28` and the
  fall-through branch of `model_training.py:106-107`). Feature count 48 / 24 / 24 / 12.
* `dl_0.5s` — a separate matrix of 48 columns built with a single 0.5 s window and a 0.5 s
  update interval (`model_training.py:109-111`, which also patches the id-column index from
  288 to 48). Feature count 48 / 24 / 24 / 12.

Because `dl_0.5s` ticks twice per second, `sequence_window_size` is expressed in 0.5 s steps
for those trials. This is visible in the databases as a second distribution for the same
parameter: `IntDistribution(low=10, high=120, step=10)` for every `dl_0.5s` trial and
`IntDistribution(low=5, high=60, step=5)` for every other trial (counted over all 3,149
`sequence_window_size` values stored in the six sequence-model databases: 501 wide, 2,648
narrow, and the split is exactly by `dataset`). Both therefore mean **5-60 s of traffic
history**, which is what the paper states. The CNN's `kernel_size` upper bound likewise
varies, `min(10, sequence_window_size)` in raw steps: of the 888 stored values, 96 have
`high=5` — exactly the trials with `sequence_window_size = 5` — and 792 have `high=10`.

## 5. Feature selection

### 5.1 The procedure

Training data only, two stages, in `feature_selection.py`:

1. **Mutual information** (`feature_selection_mi`, `feature_selection.py:90-119`).
   `mutual_info_classif` for stalling and `mutual_info_regression` for buffer health, with
   `random_state=1234`, computed on the full training matrix
   (`n288_i1.0_w1-3-5-10-20-30_ffill`). Scores are sorted descending, normalised to sum to
   one, cumulated, and the features are kept while the cumulative share is `<= 0.95`
   (`feature_selection.py:111-115`). The removed tail therefore accounts for 5 % of the total
   mutual-information score.
2. **Random-forest permutation importance** (`feature_selection_pi`,
   `feature_selection.py:122-163`). A default `RandomForestClassifier`, or a
   `RandomForestRegressor` with `max_depth=8, min_samples_leaf=4`, is fitted on the first 80 %
   of the training matrix restricted to the stage-1 survivors; `permutation_importance` is
   then run on the held-out 20 % with `n_repeats=30`, `max_samples=0.1`, scoring
   `average_precision` or `r2` (`feature_selection.py:143-151`). The ranking statistic is the
   **lower bound of the 95 % confidence interval**,
   `importances_mean - 1.96 * importances_std / sqrt(30)` (`feature_selection.py:153-154`),
   and the same normalise-cumulate-keep-95 % rule is applied again
   (`feature_selection.py:155-158`).

This matches the paper's §III-A description. One caveat the paper does not mention: the
stage-2 statistic can be negative (an unimportant feature can score worse than noise), and
the code normalises by `df.sum()` before cumulating, so the cumulative curve is not monotone
when negative values are present. This is what produces the very aggressive buffer-health
removals in §5.2 — it is the behaviour of the released code, reproduced here as-is, not an
error in this document.

The procedure is run for every combination of task × view × `feature_window_size`
(2 × 4 × 4 = 32), which is why `importances/` holds 32 `permutation_importance_*.json` files.
The 33rd file in that directory, `importance_scores.json`, is unrelated: it holds Optuna
hyperparameter-importance values under the keys `score` and `energy`, not feature importances.

The stage-1 output files (`mutual_information_*.json`) are **not** in the released data.
Their content is nevertheless recoverable: the `features` key of each
`permutation_importance_*.json` file is exactly the stage-1 survivor list, because
`feature_selection.py:140-142` reads `selected_features_mi_gt_95` and writes it back as
`features`.

## 6. The offline/live mismatch

This is the one feature-design defect that a re-user has to know about. **The size features
are computed from a different field in training than in deployment**, so their numerical
scale differs between the two. The paper admits this in a single clause in §VI; the two code
paths are put side by side here.

### 6.1 Training: transport payload length

The training matrix is built from the public dataset's parquet copies. `size` is assigned per
transport protocol (`preprocessing.py:110-112`):

```python
df["size"] = pd.NA
df.loc[df["payloadprotocolnumber"] == 17, "size"] = df.loc[..., "udplen"]   # UDP / QUIC
df.loc[df["payloadprotocolnumber"] == 6,  "size"] = df.loc[..., "tcplen"]   # TCP
```

`tcpLen` and `udpLen` are the **transport payload lengths**: a pure TCP ACK has `size == 0`.
The 100 B size class is then a payload threshold (`feature_extraction_offline.py:13`):

```python
window_filtered = window_direction if j else window_direction.loc[window_direction["size"] > 100]
```

### 6.2 Deployment: IP total length, behind a frame-length BPF

The live monitor is `pipeline.py`. Capture is filtered in the kernel and the size field is
taken from the dissector (`pipeline.py:102-123`):

```python
cmd = ['tshark', '-l', '-q', '-n', '-i', 'eth0', '-f', 'ether src 00:d8:61:39:6f:02']
...
case "gt_100":
    cmd[-1] = f"{cmd[-1]} and greater 100"      # BPF, frame length
    cmd += ["-s", "96"]
...
cmd += ["-Y", f"ip.addr in {{{IPS}}}",
        "-T", "fields",
        "-e", "frame.time_epoch",
        "-e", "ip.src",
        "-e", "ip.len",                          # <- the size field
        "-E", "separator=,"]
```

and the 100 B size class is re-applied to that field (`pipeline.py:81`):

```python
gt_mask = sizes_win > 100        # sizes_win holds ip.len
```

The same two choices appear in every other live or replay path: `feature_extraction.py:28-39`
(the stored-trace feature-extraction runs) uses `frame.len > 100` and `-e ip.len`;
`capturing.py` on both devices uses `greater 100` with `-s 96`; and
`traffic_processing_{dynamic,static}.py` pass the third CSV field through unchanged as `size`.

### 6.3 The offset, and what it does

`VALIDATION.md:49` states the conversion measured on the raw traces:

> IP length = 28 + udpLen (UDP) or 52 + tcpLen (TCP, 32-byte header with timestamps);
> frame = IP + 14.

So, for every packet,

| Quantity | Training value | Live value |
|---|---|---|
| size feature | `tcpLen` / `udpLen` | `tcpLen + 52` / `udpLen + 28` |
| byte count over a window of *n* packets | Σ payload | Σ payload + 52n / 28n |
| kernel filter for the >100 B views | *(none; applied after the fact)* | frame length ≥ 100 B, i.e. payload ≥ 34 B (TCP) / ≥ 58 B (UDP)† |
| >100 B size class | payload > 100 B | IP length > 100 B, i.e. payload > 48 B (TCP) / > 72 B (UDP) |

† The `greater` primitive of `pcap-filter` is documented as `len >= length`, not `>`. That is
the libpcap manual, not a file in this artifact, so it is flagged as an external reference;
the inequality direction does not change any of the three consequences below.

Three consequences:

1. **The size and byte-count features are shifted by a constant that depends on the transport
   protocol.** A pure TCP ACK is 0 B in training and 52 B in deployment. Every mean, median,
   min and max of the payload size moves by +52 or +28; the SD does not move; the byte count
   moves by 52 or 28 times the packet count.
2. **The two >100 B views select different packet sets.** In training the class holds packets
   with more than 100 B of payload. In deployment it holds packets with more than 100 B of IP
   length, which is 49 B of TCP payload or 73 B of UDP payload. The BPF `greater 100`
   primitive is moreover `len >= 100` rather than `> 100` (see the footnote above), and it is
   evaluated on the frame, so the kernel already keeps packets the offline definition
   excludes. The paper's §III-C statement
   that "filtering is based on frame length, with remaining small packets discarded after
   dissection" is correct for the live path; what it does not say is that the second-stage
   threshold is on IP length and that the training-time threshold was on transport payload.
3. **Models trained on the offline features cannot be expected to transfer to the live
   features.** `PILOTS.md` §7.5-7.6 is the supporting evidence, and it should be quoted
   precisely. What §7.5 *measures* is the TCP-vs-QUIC shift, where the uplink size features
   differ by a comparable constant (median uplink size 0 B for TCP vs. 47 B for QUIC; downlink
   full-size payload 1,368 B vs. 1,358 B) and where cross-protocol average precision collapses
   from 85 % to 3-12 % and R² from +88 % to between −125 % and +28 %. §7.6 then names the
   offline/live offset as the same kind of constant-offset shift, "+52 B TCP, +28 B UDP, per
   `sim/VALIDATION.md`", and states that features based on IP or frame length "were **not**
   tested here". **The non-transfer of the offline/live offset is therefore an inference from
   a measured protocol shift of the same form, not a direct measurement.** The mechanism §7.5
   identifies — tree ensembles split on exact size values — applies to both.

### 6.4 What this means for reproduction

The full-test scores reported in the paper (Figure 2 and the offline-benchmark Table III) are offline scores: the same
feature definition was used to train and to test, so they are internally consistent. The live
workload W2 measures **energy and timing**, not score, so the mismatch does not invalidate any
energy number. It does mean that the exported ONNX models are not deployable against the live
feature extractor without either recomputing the training features from IP length or
subtracting the per-protocol offset at inference time. Neither was done.

## 7. Missing values

Per-run forward fill, then drop (`preprocessing.py:349-353`, inside the per-run loop of
`build_datasets_from_config`):

```python
for j, run in enumerate(tqdm(runs_stage)):
    df = pd.read_parquet(.../f"samples_from_config/{dataset}/{run}_samples.parquet")
    match handle_missing:
        ...
        case "ffill":
            data_run = df.ffill().dropna().to_numpy(dtype=np.float32)
```

The datasets the paper uses are the `ffill` variants (`model_training.py:40` and `:120`,
`run_models.py:38`). The pipeline also implements `na`, `bfill`, `fbfill` and `fill-1`; those
variants were not used for the released models. After concatenation the whole matrix is
clipped at zero, `np.clip(data, 0, None)` (`preprocessing.py:363`), which also removes the
NaN-free but negative inter-arrival times that `merge_asof` repair can introduce.

Two properties follow:

* **Forward fill is per run.** It never carries a value across a run boundary, because the
  loop reads one run's parquet file at a time. This is the correct behaviour and it is worth
  stating, since the concatenated matrix gives no visual clue.
* **`dropna()` is what makes the per-run sample counts vary.** A second whose longest window
  is empty is written as `pd.NA` (`preprocessing.py:291`); forward fill repairs it from the
  previous second. At the *start* of a run there is no previous second, so every leading
  second whose 30 s window is sparse is dropped outright. Runs differ in how many such
  seconds they have, so the number of samples a run contributes is not its duration in
  seconds. The per-run `(run, offset, length)` triples the pipeline writes alongside each
  dataset (`index_{name}.npy`, `preprocessing.py:360` and `:374`) would give the exact
  per-run counts; **those index files are not part of the released data**, so the per-run
  distribution cannot be reconstructed here.

## 8. Sample definition and test population sizes

### 8.1 One sample per second with a complete history

A sample is emitted once per `execution_interval` (1 s), starting at the first packet of the
run, for as long as the clock is before the run's last packet
(`preprocessing.py:284-295`). A second is skipped entirely if the longest window
contains no packet (`preprocessing.py:292-293`), and the sample is labelled with the id of
the **last packet in the longest window** (`preprocessing.py:294`). That id indexes the
per-second application log through `matrix_application_link`, which was built with
`pd.merge_asof(..., direction='nearest')` (`preprocessing.py:129`), so the label is the player
state nearest in time to that packet.

Targets: stalling is `phase == "stalling"` (`preprocessing.py:382`); buffer health is
`bh.mask(bh < 0).clip(0, 120000) / 120000` (`preprocessing.py:413`), i.e. seconds of buffer
normalised by a 120 s cap, which is why every reported MAE is a stored value times 120
(`machine_learning_helpers.py:251`). Samples whose buffer-health target is missing are dropped
for the regression task only (`machine_learning_helpers.py:34-35`); the classification task
keeps them. This is the whole of the 316,964 − 313,216 = 3,748-sample difference between the
two tasks.

The run split is exactly reproducible: seed 1234, `numpy.random.default_rng`, a permutation of
run ids 1..11142, then training = the first 9,018, validation = the next 1,033, test = the
last 1,091 (`helpers.py:11-14` and `preprocessing.py:334`).

```python
SEED = 1234
RNG = np.random.default_rng(SEED)
NUMBER_OF_RUNS = 11143
RND_RUNS = RNG.choice(a=range(1, NUMBER_OF_RUNS), size=NUMBER_OF_RUNS-1, replace=False)
...
runs = [RND_RUNS[0:9018], RND_RUNS[9018:10051], RND_RUNS[10051:11142]]
```

### 8.2 Why the populations differ, and by how much

Counts below are `len()` of the stored full-test prediction arrays in
`data_masters_thesis/general_data/{stalling,buffer_health}_predictions/*_predictions.npy`, one
per role entry (96 files). The per-configuration value is the `test_population` column of
`data/features/configurations.csv`.

Three mechanisms reduce a population below the raw count:

1. **Input history.** `generate_windows` (`machine_learning_helpers.py:44-65`) builds one
   window per sample and then drops the last `window_size` windows of each run, so a model
   with *h* seconds of history loses *h* samples per run — and contributes nothing at all for
   runs shorter than *h*. This is not linear in *h* once short runs start dropping out.
2. **Last-batch truncation in the neural path.** The evaluation `DataLoader`s use
   `batch_size=128, drop_last=True` (`model_training.py:168` and `:172`), and the script that
   produced the stored arrays truncates to a whole number of batches,
   `n_samples = len(data) - len(data) % batch_size` with `batch_size = 128`
   (`run_models.py:42` and `:69`). Every array produced that way is a multiple of 128.
3. **Target-missing removal** for buffer health (§8.1).

Non-sequence families:

| KQI | Family | Full-test samples | Multiple of 128 |
|---|---|---|---|
| stalling | RF, LGBM | **316,964** | no |
| stalling | FFNN | **316,928** | yes (316,964 truncated) |
| buffer health | RF, LGBM, FFNN | **313,216** | yes |

The FFNN uses no history at all, yet loses exactly 36 samples relative to the trees: that is
mechanism 2 alone, and it is the cleanest demonstration that the truncation is real. The 16
stalling tree arrays are the only ones in the whole set of 96 that are not multiples of 128,
so they must have been produced with the truncation disabled. The buffer-health raw count of
313,216 happens to be a multiple of 128 itself, so the tree and FFNN buffer-health arrays
cannot be distinguished on that basis. **Which run of `run_models.py` produced which stored
array cannot be determined from the released data.**

Sequence families: the population is a deterministic function of the KQI and the selected
history length. Every configuration with the same pair has the same count.

| KQI | History [s] | Role entries | Full-test samples |
|---|---|---|---|
| S | 5 | 3 | 311,424 |
| S | 10 | 1 | 306,048 |
| S | 15 | 3 | 300,544 |
| S | 20 | 2 | 295,040 |
| S | 25 | 3 | 289,664 |

| S | 40 | 2 | 273,664 |
| S | 45 | 5 | 268,416 |
| S | 50 | 1 | 263,296 |
| S | 55 | 3 | 258,304 |
| BH | 5 | 4 | 307,712 |
| BH | 20 | 1 | 291,456 |

Across all 96 role entries the full-test population ranges from **249,600** to **316,964**, a
spread of 21.3 % of the maximum. Restricted to the sequence families the range is
249,600-311,424, which is the range the paper's §III-F gives. The paper's statements
"316,964 stalling samples (316,928 for FFNNs)", "313,216 buffer-health samples for
non-sequence models" and "for sequence models, the number of samples ranges from 249,600 to
311,424" all reproduce exactly.

Cross-family score comparisons in Figure 2 are therefore made on populations that differ by up
to 21 %. The paper attributes the variation only to input histories; mechanism 2 is the second
cause and is not mentioned in §III-F.

The separate **offline benchmark subset** used for the W1 energy measurements is a different
population: 100,000 samples drawn once with a fixed seed and shared across all models
(`methodology.tex:159`). It is not affected by any of the above.
